PART 0  -  THE BIG PICTURE  (read me first)
================================================================================

WHAT THIS PROJECT IS
A faithful digital reproduction ("clone") of ONE page — the homepage — of the
real website "Conejo Valley Family Counseling," a family-therapy practice in
Newbury Park, California. The clone recreates the page's layout, colors, fonts,
images, and section-by-section wording, but rebuilds it with modern web
technology instead of the original site's platform (which was Squarespace).

IN PLAIN TERMS
Imagine you love a printed brochure and want to reprint it with your own press.
The content and look are the same, but the "printing press" behind it is new.
Here, the brochure is a single web page, and the new press is a coding toolkit
called Next.js. The result is a fast, professional-looking web page that can be
published on the internet.

WHY CLONE A HOMEPAGE? (legitimate uses)
  - Learning: rebuilding a polished page teaches layout and styling skills.
  - Prototyping: get a realistic mockup a designer can refine.
  - Migration: move a client off an expensive/limited platform to a system
    the team fully controls.
  - Rebranding base: reuse the structure, swap in your own content later.

IMPORTANT HONEST NOTE ABOUT SCOPE
This repository contains ONLY the homepage. The navigation and footer link to
other pages (Contact, FAQs, team bios, individual service pages) that are NOT
built here. This is a real limitation explained fully in PART 7.

################################################################################
2.1  BUILD & TOOLING LAYER
################################################################################
WHAT IT IS / ROLE
The invisible machinery that turns human-written source code into a finished,
fast website that a browser can load. Every other component depends on this
layer to function.

HOW IT WORKS
When a developer runs "npm run build", Next.js reads app/ and components/,
converts JSX/TSX into browser-ready JavaScript, compiles globals.css (and all
Tailwind classes) into one optimized stylesheet, and emits finished HTML for the
homepage. Because the homepage has no live data, it can be "pre-rendered" — the
final HTML is produced ahead of time. Project scripts:
    npm run dev     -> start a local development server on http://localhost:3000
    npm run build   -> produce the optimized production build
    npm run start   -> serve the built site locally
    npm run lint    -> check code for problems (ESLint)

Key configuration (next.config.ts) enables:
  - Turbopack (Next's fast bundler) with a rule to process *.css via Tailwind.
  - Experimental features: agentFeedback; cacheComponents:
    partialPrefetching.
Files: package.json, next.config.ts, tsconfig.json, eslint.config.mjs
Evidence it works: final-check.txt shows "Compiled successfully", TypeScript
passing, and the "/" route prerendered as static.

TECHNOLOGIES
  - Next.js 16 (App Router, React Server Components, static generation)
  - Turbopack (bundler/dev server)
  - TypeScript 5 (config + type checking of .ts/.tsx)
  - ESLint 9 + eslint-config-next (code quality)

REAL-WORLD USE CASES
  Any modern website needs a build step. This toolchain pattern is used by
  marketing sites, docs, blogs, e-commerce storefronts, and dashboards.

EDGE CASES / FAILURE SCENARIOS
  - Experimental flags (cacheComponents, partialPrefetching, agentFeedback)
    may change or break across Next.js minor/patch upgrades.
  - Turbopack vs. Webpack differences: some plugins only support one or the
    other, so adding uncommon plugins later could fail.
  - TypeScript "strict": true means small type slips block the build.
  - The odd "allowScripts" key in package.json is a package-manager
    install-script gate (unrs-resolver); unusual and non-standard.

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Pin and review experimental flags; disable ones you don't rely on.
  - Add an "engines" field to lock the Node.js version used for builds.
  - Add a CI check that runs "build" + "lint" so regressions fail loudly.
  - Consider removing experimental flags for a stable production build.


################################################################################
2.2  THEMING / DESIGN SYSTEM (global look & feel)
################################################################################
WHAT IT IS / ROLE
Defines the site's colors, fonts, spacing, and reusable button/animation styles
ONCE, so the whole page stays visually consistent and easy to "re-skin."

HOW IT WORKS
globals.css is the single source of truth:
  1. "@import tailwindcss" pulls in the Tailwind engine.
  2. An "@theme { ... }" block declares design tokens, e.g.:
        --color-ink        #2b2b2b   (near-black text)
        --color-sage       #86b3b3   (calm teal accent)
        --color-cream      #e3d9ca   (warm tan sections)
        --color-cream-light#f6f4ee   (very light cream)
        --color-line       #515151   (button underline)
        --color-line-soft  #d8d2c4   (card divider)
        --font-display     "Beaufort Pro", Georgia, serif
        --font-script      "PrintedMoments", ... cursive
        --font-sans        Muli, "Helvetica Neue", ... sans-serif
        --spacing-site     1800px    (max content width)
  3. Custom utility classes add behavior: .btn-primary (underline wipes on
     hover), .btn-pill (rounded outline button), .nav-underline, .eyebrow
     (small uppercase label), .reveal-on-scroll (fade/slide in), .scroll-progress
     (top reading bar), .back-to-top.
  4. Typography rule: body uses Muli; headings use Beaufort Pro; the special
     "script" accent words (<strong><em>...</em></strong>) print in PrintedMoments
     in the sage color — e.g. the word "Thrive" in the hero headline.
  5. Base font-size is set to 15px on <html> for the site's proportions.
File: app/globals.css

IN PLAIN TERMS
A "design system" is like a brand style guide that the code reuses
automatically: pick colors and fonts in one place, and every headline, button,
and section uses them. Change one color token and the whole site re-skins.

TECHNOLOGIES
  - Tailwind CSS v4 (utility-first styling with CSS-based @theme tokens)
  - CSS custom properties (variables)
  - @font-face declarations for self-hosted fonts

REAL-WORLD USE CASES
  Consistent branding across large sites; fast white-label re-skinning; handing a
  coherent style kit to designers and developers.

EDGE CASES / FAILURE SCENARIOS
  - Custom fonts fail to load (missing files, blocked requests) -> site falls
    back to Georgia / generic cursive / system sans silently.
  - Tailwind v4's CSS-first config means the "utility" names depend on tokens;
    renaming a token can break classes referencing it.
  - Script accent color (sage) relies on a specific font; if PrintedMoments is
    absent, the "handwritten" feel is lost.
  - min-h using vh and aspect-ratio boxes can behave oddly if font metrics shift.

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Verify font files exist and consider font-display: swap (already set).
  - Add a subtle color-contrast check (e.g., sage text on white).
  - Keep a documented token list for designers.
  - Alternatively load fonts via next/font for automatic optimization/no
    layout shift.


################################################################################
2.3  APP ROUTER SHELL (layout + page)
################################################################################
WHAT IT IS / ROLE
The frame around every page. app/layout.tsx defines the document skeleton and
site-wide settings; app/page.tsx is the homepage itself and decides which
sections appear and in what order.

HOW IT WORKS
layout.tsx (the "frame"):
  - Renders <html>/<head>/<body>, imports globals.css, sets lang="en".
  - Declares the SEO metadata (see 2.7).
  - Pre-connects to Google Fonts and loads Muli.
  - Renders a "Skip to content" accessibility link that jumps to #main.
  - Wraps {children}; the current Next.js typing uses LayoutProps<"/">.
page.tsx (the "assembly"):
  - Imports all section components and renders them top-to-bottom inside <main>:
        Header -> Hero -> Intro -> WhoWeHelp -> QuoteBanner -> Expertise ->
        HowWeWork -> Honoring -> Specialties -> AppointmentCTA
    then Footer, then SiteEnhancements (the scroll widgets).
Files: app/layout.tsx, app/page.tsx

IN PLAIN TERMS
layout.tsx is the picture frame and page settings that stay the same for every
page. page.tsx is this specific page: it lists the sections in order, like
stacking building blocks from top to bottom.

TECHNOLOGIES
  - Next.js App Router, React Server Components (layout/page are server
    components by default — they render to HTML on the server)
  - Next.js <Image>-based components live inside children, not here

REAL-WORLD USE CASES
  Every multi-page React/Next site uses this shell pattern to share headers,
  footers, fonts, and metadata.

EDGE CASES / FAILURE SCENARIOS
  - metadataBase is set to the real production domain; if you deploy elsewhere,
    social-share URLs (Open Graph / Twitter) would be wrong.
  - The layout references LayoutProps<"/"> (a narrow type); adding more pages
    later is fine, but this typing is route-specific.
  - Fonts loaded from Google are an EXTERNAL network dependency: in China or
    offline, Muli won't load (graceful fallback applies).

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Make metadataBase dynamic from an environment variable / VERCEL_URL.
  - Consider next/font to avoid the external request.
  - Add a custom app/not-found.tsx for friendly 404s (see PART 7).


################################################################################
2.4  SERVER (PRESENTATION) COMPONENTS
################################################################################
WHAT IT IS / ROLE
The visible content blocks of the homepage. These are "Server Components" —
they contain no interactivity, so they are rendered to plain HTML once (fast,
small, great for SEO). They compose the actual page copy and imagery.

HOW IT WORKS (each is a small function returning JSX)
  - Hero.jsx: two-column layout — large lifestyle photo (left) + eyebrow,
    H1 headline "Rebuild your foundation ... Thrive", short paragraph, and a
    "Book an Appointment" button. A second photo peeks in from the right edge
    (decorative, only on xl screens).
  - Intro.jsx: empathetic copy + a beach photo.
  - WhoWeHelp.jsx: maps over an "audiences" array (Adults, Couples, Children &
    Teens), rendering a card each with image, title, description, and
    "Learn more" link.
  - QuoteBanner.jsx: full-width dark image with a 55% ink overlay and a centered
    pull-quote.
  - Expertise.jsx: two columns of "areas of expertise" keywords; items WITH an
    href become links, items WITHOUT become plain text.
  - HowWeWork.jsx: warm-cream section describing the therapy process + photo.
  - Honoring.jsx: emotional headline "Honoring where you've been & helping
    shape where you're headed." + photo.
  - Specialties.jsx: 2x2 grid of 4 specialty cards (Trauma, EMDR, Dissociation,
    Special Needs Parenting) each with body copy and "Learn More" link.
  - AppointmentCTA.jsx: centered "Schedule an Appointment" call-to-action,
    flanked by two decorative photos (lg+ screens).
  - Footer.jsx: brand block, three link columns (Navigate / Our Team / Contact
    with address, email, phone), and a sage legal bar (Terms / Privacy /
    Disclaimer / credit to the original web designer).
All images use next/image with descriptive alt text (decorative images use
alt=""), correct aspect ratios, fill layout, and responsive "sizes".

IN PLAIN TERMS
These are the words and pictures a visitor actually sees, section by section,
from the top of the page to the footer. Because they don't "do" anything
themselves, the site can show them instantly without waiting on the browser.

TECHNOLOGIES
  - React (Server Components), Next.js <Image> optimization, JSX, Tailwind
    utility classes, semantic HTML (h1–h4, <article>, <address>, <blockquote>)

REAL-WORLD USE CASES
  Marketing homepages, "about us" pages, service/catalog displays, landing
  pages — anywhere content-heavy sections should be fast and indexable.

EDGE CASES / FAILURE SCENARIOS
  - Every "Learn more"/nav link points to OTHER pages that don't exist in this
    homepage-only build -> clicking leads to 404 (major; see PART 7).
  - Images depend on files in public/images; a missing file shows a broken
    image or blank area.
  - Long, hard-coded copy can overflow on very small/variant screens.
  - alt="" on decorative images is correct, but the QuoteBanner text sits over
    an image -> contrast must remain readable (overlay helps).

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Move repeated content (team list, specialties) into a data file or CMS so
    it's editable without touching code.
  - Create the missing routes, or convert dead links to in-page anchors /
    external URLs.
  - Add automated visual/a11y tests.
  - Consider MDX or a headless CMS for copy management.


################################################################################
2.5  CLIENT (INTERACTIVE) COMPONENTS
################################################################################
WHAT IT IS / ROLE
The parts that respond to the user. These are marked "use client" so they ship
JavaScript to the browser and run there (state, events, timers). They provide
navigation and motion polish.

HOW IT WORKS
  Header.jsx (client):
   - Sticky top bar, translucent cream with a light blur, thin bottom border.
   - Desktop nav: plain links (About, FAQs), Contact pill, and three Dropdown
     menus (Our Team, Specialties, Methods). Dropdowns open on hover OR click,
     close on Escape/blur, and manage ARIA (aria-expanded, aria-controls) and
     tabIndex for accessibility.
   - Mobile: a burger button toggles a full menu. Mobile groups expand/collapse.
   - Accessibility/usability details: Escape closes menus; opening the mobile
     menu locks body scroll (document.body.style.overflow = "hidden").
  SiteEnhancements.jsx (client):
   - Top "scroll progress" bar that grows as you read.
   - "Back to top" button that appears after 600px and smooth-scrolls up.
   - "Reveal on scroll" animation using IntersectionObserver (elements fade/slide
     in once). Respects prefers-reduced-motion: if reduced motion is on, all
     reveals are shown immediately and no animation delays are used.
Files: components/Header.jsx, components/SiteEnhancements.jsx

IN PLAIN TERMS
These components make the page feel alive: the menu that drops down when you
hover, the mobile menu that slides, and the little touches like a progress bar
and a "back to top" button — plus honoring your device's "reduce motion"
accessibility setting.

TECHNOLOGIES
  - React hooks (useState, useEffect, useRef), DOM events, IntersectionObserver,
    window.matchMedia, next/link client-side navigation, inline CSS variables
    ("--scroll-progress")

REAL-WORLD USE CASES
  Navigation bars, menus, scroll effects, and progressive enhancements on
  virtually all production websites.

EDGE CASES / FAILURE SCENARIOS
  - Dropdown "hover to open" can be flaky on touch devices / across the gap
    between button and menu (mouse-leave closes it).
  - Locking body scroll must be reset on unmount; if it isn't in every path,
    the page can get stuck unscrollable.
  - No keyboard "focus trap" inside the mobile menu; Tab can move to hidden
    links behind the overlay.
  - The scroll listener re-renders state on every scroll event (throttle/rAF
    would be smoother on low-end devices).
  - Hidden-but-focusable elements (opacity animations) can harm a11y if not
    handled with visibility (the dropdown uses invisible + translate).

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Throttle the scroll handler with requestAnimationFrame.
  - Add a focus trap + return focus to the burger on close.
  - Prefer click/tap on touch and only hover on pointer-fine devices
    (media query (hover:hover)).
  - Consider a headless UI library (Radix / Headless UI) for accessible menus.

2.6  STATIC ASSETS (fonts + images)
################################################################################
WHAT IT IS / ROLE
The raw files the page serves verbatim: brand photos, the logo, and the fonts
that give the site its personality.

HOW IT WORKS
Everything in public/ is served from the site's root. Images (hero-1.jpg,
hero-2.jpg, intro.jpg, adults.jpg, couples.jpg, children.jpg, howwework.jpg,
honoring.jpg, quote.jpg, appointment-1.jpg, appointment-2.jpg, logo.png) are

italic.woff2, printedmoments.woff) are self-hosted and declared via @font-face
in globals.css so they don't depend on third parties.
Files: public/images/*, public/fonts/*

IN PLAIN TERMS
These are the "stock" materials — the actual photographs of beaches and
families, the clinic's logo, and the fancy typography fonts. Self-hosting fonts
means the site controls its own loading instead of relying on another company's
server.

TECHNOLOGIES
  - next/image (optimization, responsive images, lazy loading)
  - WOFF2/WOFF web fonts + @font-face
  - Google Fonts for body text (Muli) via a <link> in the layout

REAL-WORLD USE CASES
  Any content/marketing site; self-hosted fonts are a best practice for speed,
  privacy, and reliability.

EDGE CASES / FAILURE SCENARIOS
  - Missing/mis-renamed image or font files -> broken images or fallback fonts.
  - README image names are OUT OF DATE (it lists hero.jpg/trauma.jpg/
    specialties1-3, but the real files are hero-1/hero-2, intro, honoring,
    appointment-1/2, quote). Confusing for new contributors.
  - Leftover default files (window.svg, vercel.svg, next.svg, globe.svg,
    file.svg) and Screenshots PNGs bloat the repo.
  - Large un-optimized images increase page weight/load time.
  - External Google Fonts dependency can be blocked by networks/policies.

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Compress/convert images (WebP/AVIF), verify all referenced files exist.
  - Update README to match real files; delete unused SVGs and Screenshots.
  - Fully self-host Muli too (or migrate all fonts to next/font).
  - Add an image preload for the largest hero image (priority) — already used.


################################################################################
2.7  SEARCH / SHARING METADATA
################################################################################
WHAT IT IS / ROLE
Hidden information that tells search engines and social platforms how to
describe and display the page. It does not appear in the visible design but
greatly affects how the site is found and shared.

HOW IT WORKS
Declared in app/layout.tsx as an exported "metadata" object:
   - title + description (what shows in Google results)
   - keywords
   - authors
   - openGraph (title/description/siteName/url/type) for Facebook/LinkedIn
   - twitter card settings (summary_large_image)
   - metadataBase URL for resolving relative links
Files: app/layout.tsx

IN PLAIN TERMS
It's the page's "business card" for search engines and social apps: the title,
one-line description, and preview info people see when the link is shared.

TECHNOLOGIES
  Next.js Metadata API (static metadata)

REAL-WORLD USE CASES
  Improving Google ranking signals, click-through rates, and rich social
  previews. Essential for public-facing sites.

EDGE CASES / FAILURE SCENARIOS
  - No dedicated og:image / twitter:image referenced -> social previews lack a
    preview picture.
  - metadataBase hard-coded to production domain -> wrong URLs if deployed
    elsewhere or run locally.
  - All metadata is static; a multi-page site would need per-page metadata.

FIXES / IMPROVEMENTS / ALTERNATIVES
  - Add an og:image (1200x630) asset + twitter image.
  - Derive metadataBase from an environment variable or deployment URL.
  - Add per-page metadata + a sitemap.xml and robots.txt.


################################################################################
2.8  BACKEND, DATABASE, API, AUTOMATION — STATUS IN THIS PROJECT
################################################################################
Because a full breakdown usually names a backend, a database, APIs, and
automation, here is the honest status of each IN THIS PROJECT, and what each
would mean.

  BACKEND SERVER .............. NOT NEEDED / NOT PRESENT.
     A homepage with no live logic can be pre-built into static files, so there
     is no custom application server to write or maintain. If the project grows
     (appointments, login, forms), you would add either Next.js Route Handlers /
     Server Actions (APIs inside the same app) or a separate service.

  DATABASE .................... NOT PRESENT.
     There is nothing to store: content is written directly into the JSX
     components. If content becomes frequently edited, move it to a headless
     CMS (e.g., Sanity, Contentful) or a database, then fetch it at build time.

  REST / GraphQL APIs .......... NOT PRESENT.
     No external data is fetched. If you integrate (e.g., a booking system or
     newsletter), you'd call APIs from Route Handlers or client code.

  AUTOMATION ................... PARTIAL, AT THE BUILD/DEPLOY LEVEL.
     There is no business-process automation, but the "build then deploy" flow
     IS an automation pipeline: source code -> "npm run build" -> static files
     -> CDN. Hosts like Vercel/Netlify run this automatically when you push
     code, serve the files worldwide, and handle caching/rollbacks.

IN PLAIN TERMS
This page is like a printed poster: all the information is baked in ahead of
time, so you don't need a cashier, a filing cabinet, or a phone line to hand it
to people — you just need a fast way to print and distribute copies (the build
and hosting). Those other tools only become necessary if the poster needs to
talk back to you (collect appointments, logins, messages).

             ├─ <QuoteBanner/> (server) — full-width quote
             ├─ <Expertise/>   (server) — keyword lists
             ├─ <HowWeWork/>   (server) — process copy + image
             ├─ <Honoring/>    (server) — headline + image
             ├─ <Specialties>(server) — 4 specialty cards
             └─ <AppointmentCTA>(server) — schedule CTA
         <Footer/>           (server) — links + contact + legal
         <SiteEnhancements/> (client) — progress bar, back-to-top, reveals
--------------------------------------------------------------------------------
Everything visually sits inside layout.tsx. page.tsx chooses the order.
"Server" components render to HTML up front; "client" components add
interactivity in the browser. globals.css styles them all via Tailwind + tokens.

DATA FLOW
--------------------------------------------------------------------------------
1) BUILD-TIME (developer -> site):
      Source (app/ + components/ + public/) 
        -> next/turbopack compile (JSX->JS, TS check, Tailwind->CSS)
        -> static HTML/CSS/JS for "/"  (final-check.txt: "/" prerendered)
        -> deploy to CDN (Vercel/Netlify)

2) RUNTIME (browser):
      User requests the page
        -> CDN returns prebuilt HTML (instant visible content)
        -> Browser loads CSS + fonts + images (next/image lazy-loads below fold)
        -> React "hydrates" the client components (Header, SiteEnhancements),
           which then attach click/scroll/observer behavior.

3) INTERACTIONS (client-only, no server round-trip):
      Hover/click a dropdown -> React state toggles the menu.
      Open mobile menu -> body scroll lock; Escape/keyboard closes it.
      Scroll the page -> progress bar + back-to-top update; IntersectionObserver
        reveals sections.
      Click a nav/CTA link -> next/link routes to another page
        (NOTE: in this build most of those routes return 404 — see PART 7).

4) FEEDBACK LOOP (developer):
      Change code -> rerun build -> preview -> fix issues -> repeat.
      final-check.txt is a captured "feedback" snapshot proving the loop passed.

IN PLAIN TERMS
First the "studio" prints the page ahead of time and ships copies close to
visitors. When someone opens it, the page shows immediately, and small bits of
JavaScript "wake up" to handle the menu, scrolling, and animations — without
needing to phone back to the studio for each click.

PART 7  -  CONSOLIDATED EDGE CASES, RISKS & RECOMMENDATIONS
================================================================================

TOP ISSUES (highest impact first)
  1. DEAD LINKS TO NON-EXISTENT ROUTES  [HIGH]
     Header/Footer/CTAs link to /contact, /faqs, /therapists-newbury-park, and
     individual therapist/service slugs, but only "/" exists. Visitors who click
     will hit 404 pages.
     Fix: build those routes (even as simple placeholder pages), or point links
     to in-page anchors (#appointment) / external booking URLs. Add a custom
     app/not-found.tsx with a friendly message and a link home.

  2. OUTDATED README  [MEDIUM]
     README lists components and image filenames that no longer match reality.
     Fix: update the file map and image table to the real files.

  3. REPO BLoat / DEAD ASSETS  [MEDIUM]
     Leftover default SVGs and Screenshot PNGs sit in public/.
     Fix: delete unused assets; keep public/images + public/fonts only.

  4. EXPERIMENTAL NEXT.JS FLAGS  [MEDIUM]
     cacheComponents / partialPrefetching / agentFeedback can break on upgrades.
     Fix: pin versions; disable flags you don't need; test before upgrading.

  5. METADATA BASE HARD-CODED  [LOW-MED]
     Points to the production domain even when running locally.
     Fix: read metadataBase from an env var / deployment URL. Add og:image.

  6. NO TESTS  [MEDIUM]
     Nothing guards against visual/regression/a11y breakage.
     Fix: add a smoke test (e.g., Playwright/Vitest) + an a11y check
     (axe) + a Lighthouse CI budget.

ACCESSIBILITY / UX NOTES
  - Strengths already present: skip link, semantic headings, alt text
    (empty alt for decorative), ARIA on menus, focus-visible outlines,
    prefers-reduced-motion handling.
  - Gaps to close: focus trap + focus restore in the mobile menu; ensure all
    interactive text meets color contrast (sage on white; white on the quote
    overlay); verify keyboard operation of hover-only dropdowns via touch.

PERFORMANCE NOTES
  - Add requestAnimationFrame throttling to the scroll listener.
  - Ensure hero image uses priority (it does) and below-fold images lazy-load
    (next/image default).
  - Optimize images (WebP/AVIF) and self-host all fonts.

SECURITY NOTES (relevant only if extended)
  - No secrets or env files are committed (good; .env* is git-ignored).
  - When you later add forms/APIs, add input validation, rate limiting, and
    HTTPS-only assumptions; never log personal/PII data (this is a healthcare
    context, so privacy matters).

PART 8  -  PLAIN-ENGLISH GLOSSARY
================================================================================
  Next.js .......... a toolkit for building websites with the React library.
  React ............ a popular way to build interactive user interfaces.
  Tailwind CSS ..... a styling toolkit where you compose pre-made style
                     "utilities" instead of writing custom CSS each time.
  @theme / tokens ... named colors, fonts, and spacing reused across the site.
  JSX / TSX ........ code that mixes markup with JavaScript/TypeScript.
  Server vs Client
  Component ........ parts rendered on the server (fast, no interactivity)
                     vs in the browser (interactive: menus, animations).
  Static generation . building the finished page ahead of time so it loads
                     instantly.
  Hydration ........ the browser "activating" the interactive parts after the
                     static page appears.
  SEO metadata ..... hidden page info that helps search/social describe it.
  CDN .............. a global network of servers that deliver the site quickly
                     to visitors near them.
  Alt text ......... text describing an image for screen readers and search.
  ARIA ............. extra tags that describe interactive elements for
                     assistive tech.
  prefers-reduced-
  motion ........... a user setting; when on, the site avoids big animations.
  next/image ....... an optimizer/lazy-loader for images.
  Intersection
  Observer ......... a browser tool that notices when an element scrolls into
                     view (used for the reveal animations).
